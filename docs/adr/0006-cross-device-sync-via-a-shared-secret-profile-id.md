# Cross-device sync via Firestore, a shared-secret Profile ID, and whole-document last-write-wins

The app was built local-only on purpose — no backend, no accounts, one browser's `localStorage` as the entire save file. That held until a real need arrived: the same Learner practices from more than one parent's phone, and neither parent was willing to export/import a save file by hand every time they switched devices. This reverses the local-only commitment, deliberately, and this ADR is where that reversal is owned rather than left implicit in a diff.

**Firebase (Firestore + Anonymous Auth), not Supabase.** Offline-first — keep answering Facts with no network at all, sync automatically once reconnected — was a hard requirement, not a nice-to-have. Firestore's client SDK ships that as a config flag (`persistentLocalCache`): offline writes queue against an IndexedDB-backed cache and replay once back online, and reads are served from that same cache instantly whether or not a network exists. Supabase has no equivalent - its own documented answer for offline-first is PowerSync, a separate service bolted on top, not a `supabase-js` feature. Supabase's free tier also pauses a project after a week of inactivity, which is a bad match for an app whose own Streak mechanic (ADR 0002) exists specifically because missed practice days are the normal case, not the exception - that's exactly the usage pattern that would keep re-triggering the pause. Firebase's free "Spark" plan has no such pause, and - kept deliberately on Spark rather than the paid "Blaze" plan - has a hard $0 ceiling: heavy or abusive usage just starts failing once the daily quota is hit, never an unexpected bill.

**A Profile, not a Household.** The sync unit is one Firestore document per Learner, not one document shared by everyone in a family. This was very nearly built as a "Household" containing multiple Learners, until the multi-child case made the flaw obvious: if two different Learners' data lived in one shared document, two of them practicing from two different devices at the same moment would each read-modify-write the *same* document, and one's just-written Attempt would silently clobber the other's. Splitting the sync unit per-Learner (a **Profile** - see `CONTEXT.md`) removes that failure mode entirely: two different Learners are just two independent documents with no shared write path. This app's own UI still only ever shows one Profile at a time - nothing here builds a "create a second child's profile" flow - but the data model doesn't need a rework if that's ever wanted, because it was never Household-shaped to begin with.

**Pairing is a shared-secret link, not an account.** A Profile's document lives at `profiles/{profileId}`, where `profileId` is a 122-bit random ID (`crypto.randomUUID()`). Anonymous Auth is required on every request (`firestore.rules`: `request.auth != null`), but only as a cheap deterrent against drive-by bots - it is *not* the access boundary, and deliberately doesn't check *which* anonymous user is asking, since any device holding the right link is meant to read/write it. The actual boundary is "do you know the exact document path" - the same trust model as an unlisted Google Doc link, handed over once via a pairing link (`#/join/<profileId>`) rather than typed in each time. `firestore.rules` grants `get`/`create`/`update` on an exact document ID only, and explicitly never `list` on the `profiles` collection - without that, a signed-in stranger could enumerate every family's data even without ever guessing a specific ID.

**This is a real security tradeoff, not a rounding error, and is worth stating plainly:** anyone who ever sees a Profile's link can read and write that Profile's stats, forever, with no further check. Acceptable here because the data is a family's own times-tables practice history - not sensitive by any reasonable measure - and the alternative (a real per-device membership scheme, checked server-side via a Cloud Function) would mean writing and running actual backend code for a two-phone family app, the exact ongoing-ops burden a "no backend" project was trying to avoid in the first place.

**What a leaked link can't do, cost-wise: get you an unexpected bill.** `firebaseConfig` (the API key, project ID, etc.) ships inside the built JS on purpose - Firebase's own design is that these values aren't secret, and access control is Security Rules' job, not obscurity. Because *any* visitor to the public site gets an anonymous sign-in the same way, someone could in principle script up junk documents at unknown random IDs, burning through the daily read/write quota - a real but bounded annoyance (staying on the free Spark plan means that quota-burn is the entire blast radius, not a bill), not a way to reach any specific family's actual data without their link. Two more cheap layers worth keeping in mind if abuse ever becomes real: `firestore.rules`' existing shape validation (`isValidProfileDoc`) already rejects most junk outright, and Firebase App Check (unimplemented here, still free) would additionally verify requests are coming from the real deployed app rather than a copy-pasted config.

**Joining is a replace, never a merge.** `CONTEXT.md`'s Learner is one fixed persona - there is no legitimate notion of two histories to reconcile. If a device already has its own non-trivial local progress (any Fluency record, or a nonzero Streak) when it joins an existing Profile, the join flow shows an explicit confirmation naming both sides' Streak and Active range before replacing the local one; a device with nothing yet worth losing skips the prompt and joins straight away. Cancelling leaves the device unpaired and completely untouched.

**Conflict resolution is whole-document last-write-wins, on purpose, with no field-level merge.** Two devices genuinely writing to the same Profile at the literal same instant is a realistically rare case - one Learner, one thumb, one device usually active at a time - and the cost of getting it wrong is losing a handful of recent Attempts' Fluency/Accuracy updates, not a trust-breaking loss. That's a deliberately-accepted, self-healing failure mode, consistent with this app's existing tolerance for imprecision (ADR 0002's whole premise). Building CRDT-style field merging to close that gap would be real, ongoing complexity spent on an edge case that costs almost nothing when it does happen.

**The pure engine (`src/engine/engine.ts`) needed zero changes.** Sync is entirely a persistence/main.ts-layer concern: `persistence.ts`'s `migrate()` is reused unchanged to validate a Firestore document exactly as it already validated a `localStorage` save, and `main.ts` boots instantly from the local save (online or offline) before reconciling any live update in the background - never blocking the very first paint on a network round-trip. `muted` and `remindersEnabled` stay device-local, never synced: they describe *this device's* speaker and OS notification permission, not the Learner's shared progress, and syncing them would mean muting one phone silently mutes the other.

**A genuine, worth-naming cost: this app's first real runtime dependency.** Everything else here has stayed hand-rolled on purpose (WebAudio synthesis instead of an audio library, a screenshot script instead of an image library for icons). Firebase's SDK, lazy-loaded behind the sync toggle so a single-device household never downloads it, is still a real ~175KB gzipped the moment any household actually turns sync on - a deliberate, one-time philosophical shift this ADR is choosing to make, not something to gloss over.

**The real project's config lives in `.env.production`, deliberately not plain `.env`.** Vite loads a bare `.env` in every mode; `.env.production` only in "production" mode. `scripts/setup_firebase.py` writes to the latter, and `npm run dev`/`test:e2e`/`test:rules` all build or run in other modes on purpose, so a developer who's configured a real project for deployment never has it silently leak into their own local dev/test runs - discovered the hard way when a real `.env.production` on a dev machine made the e2e suite try to sign in against the real Firebase Auth API instead of the emulator, and (in an environment with restricted outbound network access) hang until every affected spec timed out. `playwright.config.ts` builds its own webServer with `--mode test` for the same reason - the e2e suite must never depend on, or be capable of touching, a real project.

Considered and rejected: a "Household" document holding every Learner (the concurrent-write clobbering problem above); a real per-device membership list enforced server-side (correct, but needs backend code to run and maintain); Supabase (no built-in offline story, and a pause policy actively hostile to this app's own forgiving-of-missed-days design); CRDT/field-level merge conflict resolution (real complexity for an already-rare, already-cheap-to-lose edge case); syncing `muted`/`remindersEnabled` alongside the engine state (they describe the device, not the Learner); a bare `.env` for the real project's config (the local/CI leak above).
